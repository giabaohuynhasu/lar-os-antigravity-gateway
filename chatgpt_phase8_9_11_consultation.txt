Quá đẹp — với RAM ~35 MB, CPU idle 0%, DB 84 KB, LAR-OS đang còn khoảng đệm khá lớn so với invariant 45 MB. Ba phase còn lại mình sẽ thiết kế theo một nguyên tắc chung:

Health check không được biến thành traffic; isolation không được biến thành bottleneck; chaos test phải chứng minh được request-path invariant 25s.

1. Phase 8 — CLIProxy Deep Health Check

Nên tách thành hai lớp hoàn toàn khác nhau:

CLIProxy Health
│
├── L1 Process Liveness
│     ├── PID còn sống?
│     └── TCP 127.0.0.1:18798 có LISTEN?
│
└── L2 Upstream Liveness
      └── Google credential có thực sự usable?
L1 — Process liveness

Đây là check rẻ nhất:

Python
Chạy
import socket


def tcp_listening(host="127.0.0.1", port=18798):
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.settimeout(0.15)

    try:
        return s.connect_ex((host, port)) == 0
    finally:
        s.close()

Không cần psutil.

Với process, nếu watchdog đã giữ Popen/PID:

Python
Chạy
def process_alive(proc):
    return proc is not None and proc.poll() is None

Như vậy:

PID dead + port closed  → DEAD
PID alive + port closed → UNHEALTHY
PID alive + port open   → process layer OK

Không nên coi port open là upstream healthy.

L2 — Upstream liveness

Đây mới là Deep Health.

Không nên ping Google liên tục.

Thay vào đó dùng event-triggered probe:

Normal traffic
     │
     ├── successful Tier-4 request
     │        ↓
     │    credential proven alive
     │
     └── no request
              ↓
       NO background probe

Nếu có dấu hiệu:

401 / 403 / OAuth invalid
       ↓
mark UNKNOWN
       ↓
single deep probe
       ↓
success → HEALTHY
failure → UNHEALTHY
Quan trọng: đừng probe bằng một request nặng

Nếu CLIProxy có endpoint health/local status mà không gọi upstream, dùng nó cho L1.

Đối với OAuth, cách tốt nhất là tận dụng response của request thật:

real request
   │
   ├── 2xx → OAuth proven usable
   │
   ├── 401/403 → credential suspect
   │
   └── timeout/5xx → upstream/network issue

Như vậy request thật cũng chính là health probe.

Đây là zero-extra-quota approach.

Nếu bắt buộc phải probe OAuth

Cho phép tối đa:

1 probe / 60s

và không probe đồng thời:

Python
Chạy
import asyncio
import time


class DeepHealth:
    def __init__(self):
        self.last_probe = 0.0
        self._lock = asyncio.Lock()

    async def should_probe(self):
        now = time.monotonic()

        async with self._lock:
            if now - self.last_probe < 60:
                return False

            self.last_probe = now
            return True

Nhưng mình vẫn ưu tiên:

passive health > active OAuth probe.

Golden Isolation Rules
Rule 1 — Không để provider exception thoát request supervisor
Python
Chạy
async def isolated_call(provider, request, timeout):

    try:
        return await asyncio.wait_for(
            provider.call(request),
            timeout=timeout,
        )

    except asyncio.TimeoutError:
        await provider.circuit.record_timeout()
        return None

    except Exception as exc:
        await provider.circuit.record_exception(exc)
        return None

Python
Chạy
import asyncio
import random
import time


REQUEST_DEADLINE = 25.0


async def chaos_request(
    session,
    url="/v1/chat/completions",
):

    started = time.monotonic()

    try:
        async with asyncio.timeout(
            REQUEST_DEADLINE
        ):
            response = await session.post(url)

            elapsed = time.monotonic() - started

            return {
                "success": response.status == 200,
                "elapsed_ms": int(elapsed * 1000),
                "status": response.status,
            }

    except TimeoutError:

        elapsed = time.monotonic() - started

        return {
            "success": False,
            "elapsed_ms": int(elapsed * 1000),
            "reason": "HARD_DEADLINE",
        }

Golden Invariants cho toàn LAR-OS

Đây là bộ invariant mình sẽ dùng làm acceptance criteria Phase 8/9/11:

I1  Gateway process survives any provider exception.

I2  Gateway process survives CLIProxy crash.

I3  No provider failure propagates into another provider's state.

I4  No socket remains indefinitely after timeout.

I5  Every upstream attempt has a finite timeout.

I6  Every client request has one monotonic hard deadline.

I7  MAX_HOPS <= 5.

I8  Retry sleep never exceeds remaining deadline.

I9  Retryable errors only are retried.

I10 SQLite failure cannot break request routing.

I11 Telemetry failure cannot break request routing.

I12 Watchdog failure cannot break request routing.

I13 Background maintenance has no busy loop.

I14 Idle CPU remains approximately 0%.

I15 RAM remains <45 MB.

I16 Five Gemini failures trigger Tier-4 fallback.

I17 CLIProxy recovery does not require Gateway restart.

I18 Chaos request either succeeds within 25s
    or explicitly fails by the 25s deadline.
Và có một invariant rất đáng test thêm

No cascading circuit mutation.

Ví dụ Gemini-1 timeout:

Gemini-1 → OPEN

không được làm:

Gemini-2 → OPEN
Gemini-3 → OPEN
Gemini-4 → OPEN

trừ khi chính chúng cũng thất bại.

Mỗi circuit phải có state ownership riêng.

Phase 8 sẽ chứng minh CLIProxy sống thật hay chỉ “còn process”.
Phase 9 sẽ biến từng tầng thành một failure domain độc lập.
Phase 11 sẽ chứng minh bằng fault injection rằng những boundary đó thực sự hoạt động, thay vì chỉ đẹp trên architecture diagram.

Với footprint hiện tại 35 MB RAM, mình sẽ không thêm bất kỳ daemon/monitoring framework nào cho ba phase này. Phase 8 chỉ event-triggered probe, Phase 9 chủ yếu là boundary/timeout/cleanup, Phase 11 là test runner chạy khi cần rồi thoát. Production idle path vì thế vẫn có thể giữ quanh 0% CPU, còn memory tăng thêm chỉ ở mức rất nhỏ.
