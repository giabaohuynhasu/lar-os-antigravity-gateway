28. Nuclear invariants

Mình đề nghị thêm các invariant này vào Phase 12:

N1 Provider failure != Nuclear
N2 Circuit OPEN != Nuclear
N3 CLIProxy restart != Nuclear
N4 Graceful Gateway shutdown != Nuclear

N5 Unexpected Gateway death = Nuclear
N6 Heartbeat stale >30s = Nuclear
N7 Persistent total route exhaustion >10s = Nuclear

N8 Watcher survives Gateway
N9 SOS path survives Gateway
N10 Watcher does not depend on Gateway HTTP
N11 One incident produces exactly one SOS
N12 Recovery creates no duplicate SOS

N13 faulthandler is forensic, not liveness
N14 heartbeat is liveness, not forensic
N15 PID is process liveness, not application health

N16 Nuclear path has bounded timeout
N17 Nuclear path cannot block Gateway
N18 Watcher has no busy loop

Điểm cốt lõi nhất: anti_crash_guard.py không nên được biến thành “một Gateway thứ hai”. Nó nên trở thành audit utility; Nuclear Watcher phải là một process hoàn toàn độc lập. Gateway chết thì watcher vẫn sống; watcher chết thì Windows SCM/Task Scheduler kéo watcher lên lại.

Và gmail_spark_sender.py phải được coi là Nuclear dependency, không phải Gateway dependency. Đặc biệt, code hiện tại còn dùng websockets và có bug .append(), nên mình sẽ sửa nó trước khi gọi đây là Nuclear-grade.

Nếu triển khai đúng kiến trúc này, LAR-OS sẽ có một failure hierarchy rất đẹp:

Đó là một kiến trúc khá gần với cách các hệ thống production tách service recovery khỏi failure notification; Windows SCM cung cấp lớp recovery bên ngoài process, còn heartbeat/external watchdog xử lý cả trường hợp process còn sống nhưng đã mất khả năng hoạt động.
